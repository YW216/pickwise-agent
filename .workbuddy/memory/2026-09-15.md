## search_catalog vs search_products 分工锐化（products-first 设计，用户裁定）
- 设计结论：search_products 卡片向量覆盖商品全部字段（含 introduction），模糊/语义/型号/品牌皆宜 → 定为默认主搜索；search_catalog 是"过滤器"（集合语义：结果天然全合规）但可搜索字段极窄——仅 name/brand/specs 值的字面子串（不含 introduction、不含 specs 键名）+ 品类精确 + 价格数值，同义词/语义改写必漏（conditions=['游戏'] 搜空实证）。catalog 不可替代场景：硬条件 AND 全满足保证、穷举在售清单；注意它也有 limit=10 截断，"穷举"仅在结果数 ≤ limit 时成立。
- 执行：registry 两工具 description 写明语义与字段边界（catalog 声明"可匹配字段仅…不匹配介绍文案"；products 声明"默认主搜索…非穷举"）；presale 两版工具使用原则第一条重写为 products-first + catalog 结构化对齐条款；SKILL.md 第三步同步。
- cases.json 联动：3 个预算 case（recommend_laptop_budget / recommend_headset_budget / multiturn_reference_price）expected_tools 放宽为双路/三路 any-of。
- 待 API 恢复（401 Token invalid）后全量回归：router_bench 21 例 + run_eval 20 条。
- 分工微调（用户二次裁定）："仅当…才用 catalog"改为**字段对齐可优先 catalog**（需求单一且落在品牌词/品类/预算边界/显式参数值时，一次确定性过滤省 token）；语义/模糊/拿不准 → products 主搜索兜底；两者可同轮并用。已同步 presale 两版 prompt + SKILL.md。
- 关于"catalog 作用是不是很小"的评估：静态看对齐场景占比低（20 条评测约 4 条），但它持有两个 products 结构上给不了的能力——硬条件 AND 全满足的确定性合规过滤 + 近穷举清单（products top-k 会截断漏项）；实现仅 60 行内存过滤，维护成本≈0。结论：保留为"对齐快路径 + 合规保证层"。
- **search_catalog 可搜索字段收窄（用户裁定）**：删 conditions 参数（specs 值子串匹配），可搜索字段收敛为 name/brand 字面 + 品类精确 + 价格数值——全部确定可枚举，对应 PG products 表的明确列。specs 参数条件（16GB/独显）与语义需求 → search_products 承担（BM25 对 specs 字面词命中 + dense 兜底）。同步：registry schema（删 conditions 参数+description）、catalog.py（_searchable_text = name+brand）、presale 两版 prompt、SKILL.md。冒烟：品牌字面 7 款 / 价格边界 10 款 / products 参数条件 ✅。参数条件的"合规保证"从 catalog 的确定性过滤降级为"BM25 命中 + Agent get_detail 复核"——已知 trade-off。
- **catalog 升级 SQL 直查 + app/db/ 数据访问包（2026-09-15）**：新建 app/db/ 包（__init__/connection 连接与 ping/catalog_repo 仓储：search_candidates（ILIKE+品类+价格 SQL）、search_nearest（防幻觉兜底，ORDER BY ABS(price-budget)）、get_products_by_ids、load_full_catalog、init_schema_and_seed）。catalog.py 切换 SQL 直查优先 + 本地过滤兜底（PG 不可达时同语义 Python 实现）；product_db.py 删除，mock_data/init_pg 改从 app.db 导入。
- 分工定稿：catalog = SQL 查询工具（直查 PG，数据变更即时可见——真值层唯一事实源的体现）；products = Milvus 索引检索（索引从 PG 构建，命中后快照组装）。回归：品牌字面 7 款 / 价格边界 10 款 / nearest（凌霄+预算100 → 最近价清单）全绿 ✅。
- **search_catalog 加 brand 参数（用户提议）**：brand 从 query 的隐式匹配升级为独立参数（enum 封闭集合：星海/曜石/云章/墨白/极光——虚构纪律锁定的品牌池，registry 约定 3 enum 表达值域）；SQL `brand = %(brand)s` 精确匹配（query 收窄为仅匹配商品名字面）；nearest 保留 brand 弱匹配（仅放宽预算）。链路：registry schema → catalog_repo SQL → 本地兜底 → prompt/SKILL。冒烟：brand=墨白+手机 → 7 款全列 ✅；brand+预算 2000 → 素笺 Mini 1640 命中 ✅。
- **brand enum 移除（用户纠偏）**：brand 是开放数据（新增品牌=INSERT 一行，不改代码），enum 会把数据变更变成代码变更，违反"真值层唯一事实源"。判据沉淀：**enum 只用于结构性封闭集合（category=领域结构），不用于会增长的数据值（brand）**；品牌池锁定是评测生成的 LLM 起草纪律，不是运行时值域约束——两者别混。description 改为列当前已知品牌示例+"以目录实际返回为准"。
- brand 参数化后的描述残留清理（用户提醒）：catalog.py 模块 docstring / registry description / SKILL.md 三处的旧语义描述（"品牌字面子串""specs 参数值子串匹配"）同步为参数化语义——"参数与 PG 表列一一对应：query=商品名字面（ILIKE）、brand=品牌精确、category 精确、budget_max 价格数值"。复验 ✅。

## 评测工具选型建议（用户问"是否要上专业评测 agent 工具"，纯建议未改码）
- 结论：分层引入——评测逻辑（规则断言/sandbox/用例生产）保留自研，评测基础设施（trace 存储/看板/run diff）引入 Langfuse（开源可自托管，OpenAI SDK 一行接入，与现有 sandbox 插桩同构）。
