## 收口重试逻辑可读性改造（已交付）
用户批准把 `_execute_agents()` 收口段的三重 `and` 拆成两层 `if`：

改前：
```python
if overflow and retry and self._try_compact(pack, force=True):
    for entry in self._execute_agents(overflow, self._build_pack(), mode, retry=False):
        results[entry.agent] = entry
```
改后：
```python
if overflow and retry:
    # 先压，压成了才重试——压不动就没必要重跑（上下文一样大，必然二次溢出）。
    # 注意 _try_compact 不是谓词：成功时它已经删过历史前缀、换过摘要了。
    if self._try_compact(pack, force=True):
        for entry in self._execute_agents(overflow, self._build_pack(), mode, retry=False):
            results[entry.agent] = entry
```

**理由**：`_try_compact` 有副作用（成功时删 `raw_messages` 前缀 + 换 summary + 并 products），与两个纯谓词并列在布尔表达式里会被读成"三个判断"；且正确性依赖求值顺序——若把动作挪到前面，没溢出时也会执行压缩。拆开后"先压、压成了才重试"一眼可见。**零行为变化**。

**验证**
- `pytest tests/test_p3_multi.py -q` → 5 passed
- 手动 `a5_partial_failure()` + `a6b_overflow_retry()` → 全绿 exit=0
  - a6b 实测输出印证改造路径被走到：`💾 [已压缩 4 条旧消息 → summary (148 字，商品记忆 0 款，保留 5 条)]`，断言含「handle 共被调用 2 次（丢弃轨迹，从头重跑）」「重跑轨迹 tool 对完整」

## 修复：验证脚本把 .env 参数盖掉了（2026-09-29 晚，用户实测踩到）
**现象**：`.env` 已改成 60000 / 16384 / 8000，但跑 `verify_compaction_e2e.py` 输出的仍是 `window=28000 reserve=16384 keep_recent=2500`（触发线 11616），第 3 步照旧超限。

**根因**：脚本里 `os.environ.setdefault("CONTEXT_WINDOW", "28000")`。`setdefault` 语义是「没有才设」，但 **`.env` 的值由 pydantic 从文件读取、不会进入 `os.environ`** → setdefault 每次都把脚本里的硬编码写进环境变量，而环境变量优先级高于 `.env` → **脚本把自己的预算盖在了 `.env` 上**。这是我写脚本时的设计失误。

**修复**：删掉三行覆盖 + 未使用的 `import os`；窗口配置统一由 `.env` 提供（单一事实来源）；并加一道保护——若 `trigger_line > 60000` 打印警告提示去调 `.env`，避免以后参数不合适时静默失败。

**验证**：`python tests/verify_compaction_e2e.py --turns 0` 现在打印 `window=60000 reserve=16384 keep_recent=8000`、`触发线 43616` ✓

**教训**：`os.environ.setdefault` **不能**用来表达"尊重外部配置"——dotenv 文件不在 `os.environ` 里。要么显式覆盖，要么完全不碰，别用 setdefault 造出"看起来在尊重、实际在覆盖"的假象。

## 真调中断：瞬时网络故障 + 暴露「LLM 调用零重试」（2026-09-29 晚）
**现象**：重跑验证脚本，第 1 轮 Router 调用抛 `openai.APIConnectionError`，traceback 显示 `httpcore/_sync/http_proxy.py` → `SSL: UNEXPECTED_EOF_WHILE_READING`。整个脚本崩掉。

**诊断**（临时脚本，已删）
- 系统代理：`HTTP_PROXY` / `HTTPS_PROXY = http://127.0.0.1:52047`（端口 OPEN，代理软件在跑）
- `api.deepseek.com` 走代理 → HTTP 401 ✓；**直连 → HTTP 401 ✓**（两者都通）
- **结论：瞬时网络抖动**，非配置问题、非代码问题。重跑即可。

**但这次暴露了真实的健壮性缺口：全链路 LLM 调用「零重试 + 无超时」**
- `Router.route()` / `SubAgent._complete()` / `_run_result_agent()` / `summarize()` 全是裸 `create()`，既无 `timeout=`（用 SDK 默认 600s），也无重试
- 后果：一次网络抖动 → 路由失败 → `chat()` 抛异常 → 用户看到"出错了"；若连接卡住则挂 10 分钟
- 修复方向（属 P7 harness 范畴）：只对**瞬时类**异常（`APIConnectionError` / `APITimeoutError` / 429）做指数退避重试，并显式设 `timeout=`。**不要对 400 类重试**——重试必须对应一个补救动作，否则只是重复同一个错误

## 摘要自我压缩（补救式）已实现（2026-09-29）
在「把墙推远」之上，补上"摘要不再只增不减"的根治手段。

**思路（补救式）**：越限了才动手——生成后检查长度，越限则**再调一次 LLM 把摘要自身重写为精简版**；仍越限才判失败、保留原状。平时零额外成本。

**改动 4 处**
1. `prompts/summarizer.py`：新增 `CONDENSE_PROMPT` —— 六个 `##` 标题与三个 `###` 子标题结构不变、硬事实（商品 ID / 价格 / 政策 / 错误）必留、明确该删什么（失效约束 / 已完结细节 / 重复表述 / 可推导内容）、目标 `{target_chars}` 字内
2. `agent/summarizer.py`：新增 `condense()`（输入是**摘要本身**，目标是收缩；`reasoning_effort="low"` 同 summarize；检查 `finish_reason`；输入超预算则 raise）
3. `agent/compaction.py`：抽出 `_over_limit()`；`compact()` 末尾加兜底分支——越限时调 condense（目标 = `summary_max_chars * 2 // 3` = **2000 字**），精简失败只打印不抛出，之后统一判失败
4. `tests/test_compaction.py`：新增 `test_compact_condenses_overlong_summary`（压回成功）、`test_compact_fails_when_condense_still_overlong`（压了还超则失败）

**三个关键设计点**
- 目标取上限的 2/3，给下次增长留空间，避免刚压完立刻又越限
- condense 的异常被 catch（打印后落到统一判失败）→ 保住"任何失败都零副作用"的事务语义
- 语义让步写进注释：宁可丢叙述性细节，也不能让压缩整体失效（否则上下文一路涨到溢出、整个会话崩）

**验证**：`pytest tests/test_compaction.py -q` → **15 passed**（原 13 + 新增 2）

## 黑板（fan-in）容量分析结论（2026-09-29，用户决定「后续再做」）
用户提问："黑板其实很难超限吧" / "放宽黑板的窗口就行了吧"。澄清后的结论：

- **黑板与历史是两种东西**：`raw_messages` 跨轮累积、**无界** → 需要压缩；`board_text` 单轮内产生、**有界**（最多 2 Agent × 5 步、**不含历史**）→ 只需要"容量够"，不该用压缩救。
- **上界公式**：`N × 每轮步数 × 单次工具结果上限` = 2 × 5 × 12000 字符 ≈ **10~18 万 token（理论最坏）**；实际典型 ≈ 3 万（实测 `get_detail` 每次约 1000~2000 字符）。
- **"放宽 `max_tokens`"无效**：它是**输出**预算，而黑板超限是**输入**问题——两笔账。
- **拉高窗口有效但治标**：`context_window − reserve_tokens` 同时是"压缩触发线"（想低）与"黑板判断线"（想高），**一个参数两个相反诉求**——这是之前调参绕来绕去的根源。
- **更根本的是压低上界**：工具结果上限（上界公式里唯一的乘数，12000→4000 即 ÷3）+ 最大步数下调；这两个还**顺带让压缩更容易触发**。
- **`_run_result_agent` 只检查不压缩是对的**：它的输入来自黑板渲染、压缩改的是 `raw_messages`，两者不相干；且它已有零成本的降级路径（拼接各专家最终答复，几乎无损）。
- `tool_result_max_chars = 12000` **从未被真实数据检验**，属"看起来安全"的拍脑袋值。
