## Tool schema 精简（registry.py 已改写）

### 精简约定（写进文件头注释，后续新增工具需遵守）
- description 只写「做什么 + 返回什么」，场景示例一律不放（示例是字数大头）
- 负向边界只在**易混工具间**保留一句互指：search_catalog↔search_by_reviews（结构化 vs 口碑）、search_by_reviews↔retrieve_reviews（评价→商品 vs 商品→评价），其余不写
- 取值固定的参数用 `enum` 表达（category: 笔记本/手机/耳机），既省字又拿一层值域硬约束——**这是"不写 Pydantic 校验"下唯一的免费校验层**
- 参数里的格式示例（`['16GB','轻薄']`、`['LP-01','LP-02']`）保留：教的是"参数怎么填"，不是"何时用工具"，价值高

### 实测数据（字符数）
| 区间 | 改前 | 改后 |
|---|---|---|
| description 合计 | 903 | 343（-62%） |
| parameters 合计 | 1907 | 1882（-1.3%） |
| 总计 | 2810 | 2225（-21%） |

**重要教训（估算偏差）**：最初预估"参数区能省 37%、整体省 47%"，实测参数区几乎没降。原因：
1. 参数区的成本大头是 **JSON 结构税**（`type`/`description`/`items` 这些固定 key，约 30 个参数 × 40 字符 ≈ 1200 字符），中文说明本身只占 ~600，压无可压
2. 新增的 4 个 `enum` 加回 ~120 字符，正好抵消了删减部分
→ 结论：tool schema 的可压缩空间**主要在 description**，参数区基本是硬成本。去掉 enum 只再多省 4%（2225→2105），不值，因为 enum 换来值域约束

## Tool description 编写原则（用户提出并拍板，已写进 registry.py 文件头）

**schema 里禁止写「去用别的工具」「别用 A 代替 B」这类跨工具路由，只写自我界定。**

- 判据：**「我不是什么」≠「你该用谁」**。前者是自我界定（任何 Agent 看了都成立），后者是路由指令（白名单一变就失效，甚至可能指向该 Agent 看不见的工具名，诱发幻觉调用）
- 三层职责：`schema` 管"我是什么" / `Agent prompt` 管"你该选谁" / `allowed_tools` 管"你能看见谁"
- 佐证：grep ecom 原版 registry.py（commit 4693936）的 `改用|不要用|代替|优先用` → **0 命中**，原版只写"何时用我"，从不做交叉引用。交叉引用是我们自创的，不是 ecom 惯例

## Multi-Agent 新架构方向（用户提出，1-3 已拍板，4 待讨论，代码未动）

> **教训：用户表达取舍时（如"先不做 X"）不等于授权开始做 Y，动手前必须确认。**

### 已定（用户拍板）
1. **ContextPack**：把 raw_messages + 短期记忆 + 长期记忆 + skill + 工具等打包成一个对象，一次构建、多处消费。Router 收到 ContextPack 做路由
2. **黑板（Blackboard）**：**只有多 Agent 模式才用**，是所有 Agent 共同写的地方
3. **Result Agent**：多 Agent 模式下汇总输出，**要调 LLM**（是第 4 个角色，但不是业务 Agent，**不调工具**，只读黑板）
4. **Router 决定走单还是多**：`len(scenarios)==1` → 单 Agent；`>1` → 多 Agent
5. **单 Agent 不经过 Result Agent**，直接返回结果（就是现在单 Agent 的样子）
6. **同一 Agent 在单/多模式下 prompt 不同** → **6 份独立完整 prompt**（2026-08-31 定稿，否决了"基础+模式后缀拼接"方案）。
   理由：自包含可读（打开就是模型看到的全貌）、单/多差异不限于尾部可各自调优。
   命名：GUIDE/COMPARE/CONSULT × SINGLE/MULTI；AGENT_CONFIGS 里 `prompts: {"single":..., "multi":...}`。
   现有三份基础 prompt 即 single 版底子；公共内容双维护靠 prompt-schema 一致性校验脚本兜底（扩成对 6 份都跑）
7. **Router 只输出场景列表，不做 task 改写**（2026-08-31 决定；曾讨论"场景+task"格式与 user 位置替换方案后取消）。
   每个 Agent 拿**用户原文**，自己完成职责范围内可实现的部分——防越界靠 MULTI_MODE_SUFFIX 文字约束 + Result Agent 整合去重兜底。
   否决理由：task 改写质量是单点依赖（丢约束/失真），不值得为聚焦冒险

### 架构形状
```
用户输入 → ContextPack → Router → [scenarios]
   ├─ N=1 → 单 Agent(single prompt) → 直接返回
   └─ N>1 → N 个 Agent 并行(multi prompt) → 黑板 → Result Agent → 返回
                                                            ↓
                                                   记忆更新 + 落盘
```
关键统一：**N=1 不是另一条路径，而是多 Agent 的特例**（线程池跑 N 个任务，N=1 跑 1 个）。

### 消息合并方案（2026-08-31 讨论后部分拍板）

**已拍板：**
- **单 Agent（N=1）：保留 A 现状**——new_messages 全量进 raw_messages（含工具消息），无黑板。串行对话里工具消息语义自洽，改动最小
- **多 Agent 执行视图（用户确认）**：每个 Agent 拿**完整 ContextPack**（第一版不做视图裁剪/渲染优化），自己构建 working messages（自己的 system prompt + 公共段 + 全量历史 + user 原文）；ReAct loop 中工具消息**正常保留在 working messages**；结束后每个 Agent 按黑板结构写**一条**条目（agent 级，不是工具级）——**working messages 本身执行完即弃，过程信息以黑板条目形式留存**

**业界参照（讨论时给出）**：Claude Code subagent=B 只回传报告（并行分工）；OpenAI Swarm/Agents SDK=A 全量 handoff（串行接力）；AutoGen=A 共享对话流。规律：**串行接力→A，并行分工→B**
- A 的深层问题不只是膨胀：tool 消息必须与 assistant(tool_calls) 成对，三个 Agent 的私密工作过程交错合并后语义破碎
- 推荐方案（主agent提出）：**B 为基座 + 跨轮黑板**——raw_messages 每轮只加 user 原文 + Result 整合文本；黑板条目挂 session 跨轮存，下一轮 ContextPack 注入"近期协作记录"摘要行（每条~25字，保留最近5轮 ≈200 token）。「你刚才推荐的第二个」→ 摘要行得知 LP-03 → get_detail 秒答

**待定（黑板结构讨论时一并定）：**
- 多 Agent 下 raw_messages 合并规则是否确认为 B（user 原文 + Result 整合文本，工具消息丢弃）
- 黑板数据结构（用户说稍后讨论）；黑板是否跨轮持久化（session 存储+老化淘汰）

改造后的 `ToolManager.execute_tool` 返回 **dict 信封**，但 OpenAI 的 tool message `content` 必须是 **str** → 本地模式下 ReAct 循环会报错。应改用 `execute_tool_as_message()`（该方法已存在，会 json.dumps）。
