## 历史降级实验：从「假想收益」到「证伪」

承接 2026-10-07 的 `_project_history`（按 Agent 白名单投影历史，消除工具名符号泄漏）。今天做的是**验证它到底有没有用**，结论是：**当前架构下测不到显性收益，且几乎不可能触发**。

### 关键发现 1：泄漏场景在真实流量下无法自然触发

为验证降级效果新建 `app/evaluation/cases_isolation.json`（4 条：3 条诱饵 + 1 条对照），诱饵设计是「turn1 走 presale 触发 search_products，turn2 由 consult 接管但用『再帮我搜一下』显式诱发模仿」。实测结果：

```
leak_probe_explicit_research  turn2 实际路由 = presale（预期 consult）
leak_probe_catalog_mimic      turn2 实际路由 = presale（预期 consult）
leak_probe_backtrack          turn2 实际路由 = presale（预期 consult）
leak_control_same_agent       presale，presale ✅ 对照组正常
```

**Router 把商品搜索需求 100% 正确分给 presale**，根本不给 consult 接手的机会 → 历史里不存在"consult 面对越权工具"的场景 → 降级不触发。
**推论**：降级防御的是「Router 出错」这个假设场景。前两道防线（Router 分类准确 + 执行层白名单硬拒）已足够，它是第三道冗余保险。

### 关键发现 2：我犯的两个错误

1. **没读判分器就写断言**：`check_route` 的解析规则是「先按 `|` 拆候选，再按 `/` 拆并集」。我写的 `"presale/consult|consult/presale|consult"` 被解析成「一轮该返回多个场景」，与实际单场景 `['presale']` 必然不匹配 → 3 条 ❌ 全是**断言格式错，不是模型行为错**。
2. **诱饵方向搞反**：想诱导 consult 模仿 `search_products`，但「再帮我搜一下」这类措辞恰恰**强化了路由到 presale**（它确实是商品搜索需求）→ 越权工具在白名单内，零泄漏。

### 关键发现 3：20 条主评测集只有 1 条能触发降级

- 17 条单轮 → 无历史可降级
- `multiturn_reference_price` / `multiturn_budget_change` → 两轮都是 presale（同 Agent，工具全在白名单内 → 放行分支）
- `multiturn_switch_consult` → presale→consult 切场景，**唯一可能触发**；但其 turn2 是纯知识问句（OLED/IPS），无「再搜」意图 → 不诱发模仿

## 确定性 token 测量（最终采用口径，可写简历）

用户明确要「能写进简历的数字」→ 放弃赌 LLM 行为，改走**白盒确定性测量**。
脚本 `tests/` 外的 `_tmp_measure_saving.py`（可重跑，零 LLM 消耗）。

### 实测结果

```
用例 A：真实会话（session.json，1 个工具块 retrieve_knowledge×2）
  4,967 → 4,967   省 0
  原因：retrieve_knowledge 同时在 presale/consult 白名单内 → 共享工具，
        按设计必须保留。**0 节省是正确行为，不是 bug**（这一点曾让我误判）

用例 B：含 presale 独占工具的历史（2 个 search_products 块）
  consult 视角：3,173 → 303 token，省 2,870（90.5%）
  presale 视角：3,173 → 3,173，省 0（同 Agent 不降级 = 防误伤生效）

单块均摊：约 1,435 token / 越权工具块
```

### 简历口径（重要，别写成 90.5%）

**不写 90.5%** —— 它取决于构造历史里"工具结果占比"这个构造条件，会被质疑。
**写这个**：跨 Agent 接管时，每个越权工具块约省 **1.4K token** 上下文；同 Agent 场景 0 节省（共享工具保留，零误伤）。

真实量级旁证：`leak_probe_backtrack` 3 轮 15 次 LLM 调用 / 12 次工具调用 / 76,637 token —— 轮数越多、历史累积的越权块越多，降级收益线性增长。

### 三点方法论教训

1. **先查判分器再写断言**：`check_route` 是「先按 `|` 拆候选再按 `/` 拆并集」，我写错导致 3 条假失败。
2. **诱饵可能强化而非削弱路由**：想诱发 consult 模仿商品工具，却因措辞更像商品搜索把 turn2 推给 presale。
3. **省 0 不一定是 bug**：先查为什么 0，再下结论。共享工具（retrieve_knowledge）本就应保留。
