## 压缩检测点分析（与 Pi 时序对比）
用户提供 Pi 的设计截图（压缩发生在两轮之间）。**我曾据单张截图推断"Pi 没有应急路径、只假设轮内不会溢出"——此论断已被用户否证**：Pi 同样有两道触发（预防性 = token 超阈值 183616；应急性 = API 返回上下文溢出 → 先压缩再重试）。教训：截图只体现正常时序，不体现异常路径，不能据此外推。

修正后的对比结论：
- 差异不在"有无应急路径"（双方都有），而在**应急的检测点铺在哪**
- 当前项目是"当场压缩 + 当场重试"，所以要在溢出发生处检测、上报、再收口重试 → 检测点必然分散
- Pi 若把应急收在轮间处理（记录失败 → 下轮开始压缩），则检测点仍可唯一——**这点未证实，不应作为论据**
- **当前项目"轮内溢出不可达"的论证不依赖 Pi**，是自证：触发线 167232、实测轮初 ≤30K、单轮增长 1~3K → 轮内要跨 137K 才可能溢出。且 Pi 阈值 183616 属同一量级，若其实测会话也在几十 K，应急路径同样不可达
- 应急路径不可达 ≠ 不该有（保险成本低）。真正要收敛的是**不在应急必经之路上的出口**：路由（风险已前移到入口闸门）、Result 汇总（N≤2，输入小）
- 应急路径的**最小必要检测点**：① 执行中发现溢出 ② 收口压缩重试。二者不可删

## Pi 压缩机制（读源码核实，已讲给用户）
稀疏克隆 earendil-works/pi，读 `packages/agent/src/harness/{session,compaction,runtime}` 落实结论：
- **压缩 = 追加 CompactionEntry + 前移 branchTip**，零删除。条目字段：`summary / retainedTail / tokensBefore / details / usage / fromHook`，`parentId = 当前 tip`
- 读取：`scanBranch({start: tipId, stopAtType: "compaction"})` 撞到最近 compaction 即停 → `buildContextEntries` 折叠为 `[compaction, ...其后条目]` → `sessionEntryToContextMessages` 展开为 `[compactionSummary, ...retainedTail]`
- 阈值检查挂在状态机 `checkpoint`（即两轮之间），reason 三态：`manual | threshold | overflow`；threshold 靠"最新 compaction 比本次 checkpoint 触发点更老"做自标记，无额外 checked 标志
- 关键修正：Pi 保留原文的**首要动机是分支/回放/崩溃恢复**（navigateTree、fork、branch_summary），不是为了跨轮追问。这解释了 PickWise v1"原文保留了给谁看"答不上来的问题
- 反推结论：只有将来要做"回到某轮重跑 / 多分支对比"才需要 Pi 这套 append-only 模型

## 三种上下文对象模型 + fan-in 数学（2026-09-28 晚）
- 用户指出 Pi 是单 Agent、只算一个上下文；双 Agent 有**三种上下文对象**：①子 Agent 私有 working（并行增长，守卫=每次调用前）②共享 raw_messages（跨轮增长，守卫=轮初估算，写点仅在收口）③Result 汇总输入（join 后一次构建=两条轨迹之和，守卫=汇总前估算）。**检查点多 = 每对象一个守卫，不是同一检查的重复**
- **fan-in 数学**：每次调用前检查给每条轨迹封顶 ≈ 触发线 → Result 输入 ≈ 2×触发线 → **低窗口 + 多场景轮次，Result 超线是结构性倾向，不是概率问题** → #7 在低窗口下必需（Pi 无此对象，故少一个点）
- **render 旋钮未用**：`render_blackboard(entries, max_result_chars)` 传的是与入库相同的上限（12000）→ 第二次截断恒为 no-op。Result 只需结论+证据指针，传 ~3000 可砍最坏情况 3/4（一个 settings 项 + 一处传参，待批准）
- 单 Agent 溢出处置链：handle 抛异常 → **A 全部轨迹丢弃（含溢出前的 step1-2，new_messages 是局部变量）**→ entry(overflow) → join 后 force 压缩一次 → 只重试 A（新 pack 从头重跑，retry=False 仅一次）→ 仍溢出记 failed → Result 部分失败如实告知。B 全程无感、结果原样保留；两个都溢出也兜得住（重试子集任意大小）
- 为什么不在 A 溢出瞬间压缩共享历史：写竞争 + 读者一致性。技术上 handle 入口拷贝使"当场压"碰巧安全，但设计拒绝依赖该实现细节——**把并发救援降级为串行重跑**，代价=丢弃部分工作，收益=零锁零取消零状态传递
- 防线 1 在发请求前拦下溢出 → 溢出那次调用不花 token，浪费的只是此前已完成的步骤
- N=1 单场景不走黑板/Result（reply 直返）→ fan-in 问题仅存在于多场景轮次

## RAG 模块源码分析（读毕，结论未整理给用户）
