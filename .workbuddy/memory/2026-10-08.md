### 关键发现 2：我犯的两个错误

1. **没读判分器就写断言**：`check_route` 的解析规则是「先按 `|` 拆候选，再按 `/` 拆并集」。我写的 `"presale/consult|consult/presale|consult"` 被解析成「一轮该返回多个场景」，与实际单场景 `['presale']` 必然不匹配 → 3 条 ❌ 全是**断言格式错，不是模型行为错**。
2. **诱饵方向搞反**：想诱导 consult 模仿 `search_products`，但「再帮我搜一下」这类措辞恰恰**强化了路由到 presale**（它确实是商品搜索需求）→ 越权工具在白名单内，零泄漏。

### 关键发现 3：20 条主评测集只有 1 条能触发降级

## 工具隔离设计总纲（面试口径，2026-10-08 梳理）

### 三层防线（按「模型能碰到什么」分层，而非按「代码在哪」分层）

| 层 | 机制 | 强度 | 代码位置 |
|---|---|---|---|
| 1 · 可见性 | `tools` 参数 = 白名单，模型看不到越权工具的**名字与签名** | 硬（API 层） | `orchestrator.py:63` 建 `ToolManager(allowed_tools=cfg["tools"])` → `manager.py:_filter_tools` |
| 2 · 执行 | `_tool_source` 同样只含白名单 → 越权调用落 `fail("未知工具")` | 硬（兜底） | `manager.py:execute_tool`（实测拒绝率 100%） |
| 3 · 上下文 | 历史里的越权工具块折叠为中性文本 | 硬（投影） | `context_pack.py:_project_history` |

**核心原则：靠数据结构，不靠 prompt。** 最初 4 份 Agent prompt 里有「那些工具不属于你，调用会直接失败」的文字约束（软约束，靠模型自觉），现由第 1/2 层接管，prompt 约束退化为兜底说明。

### 白名单结构（决定了混调场景罕见）

```
presale 独有(5): search_products  search_catalog  compare_products
                  get_user_favorites  recall_user_memory
consult 独有(0): （无）
共享(3):         get_detail  load_skill  retrieve_knowledge
```

**consult 无任何独占工具** → 它自己不可能产生越权调用块 → 混调只可能出现在 presale 历史里；且 presale 调共享工具时通常已拿到 ID（走查详情路径），不会同时调搜索工具。

### `_project_history` 的实现要点

- **整块判定**：`all(name not in allowed_tools for name in names)` —— 全部越权才折叠；有一个共享工具则整块保留（共享工具本就该两个 Agent 都看到）。
- **整块替换而非过滤**：折叠时构造**全新消息** `{"role":"assistant","content":_FOREIGN_BLOCK_NOTE}`，原 `tool_calls`（工具名+arguments）与后续 `tool` 消息**从未被复制**。不是"复制后再擦除"。
- **成对进出**：OpenAI 协议要求 `assistant(tool_calls)` 与 `tool` 成对（设计文档 C2），故只能整块进出，不拆单条。

### 两个已实测的边界（不是 bug，已知取舍）

1. **混调残留**：同一次响应里混调越权 + 共享工具时（`search_products` + `get_detail`），`all()` 为 False → 整块保留 → 连带泄漏越权那个。实测四种组合：A 纯越权→折叠无泄漏；B/D 混调→保留并泄漏；C 纯共享→保留无泄漏（正确）。不修的代价对比：修需按 call 粒度摘除，会把并行轨迹拆成"只查了详情、没搜列表"的失真形态，更可能诱发重复查询。
2. **原 `content` 被整句丢弃**：折叠时连 `content` 一起换成中性文案。当前模型 `content` 恒为空（思考走 `reasoning_content`，落盘只有最终答复）→ 零损失；但属**碰巧安全而非设计上安全**，代码层无防护。换模型后需重新评估（应改为"保留 content 中的用户约束、剥离工具名"）。

### 隔离级别阶梯（生产界对照，面试话术用）

L1 共享全量历史 → **L2 能力面收窄 + 越权符号降级（当前位置）** → L3 发送者标注 + 按角色过滤（LangGraph/AutoGen 那一档）→ L4 独立上下文 + 结构化交接契约（Claude Code subagent / Agents SDK handoff / MCP）。

不上 L3/L4 的理由要能说清：**跨 Agent 指代是本项目核心能力**（`multiturn_switch_consult`：presale 推荐完 → consult 答政策，consult 必须知道前面推荐了哪几款），改独立上下文会直接退化该能力。升级路径已留 seam：投影逻辑集中在 `build_working_messages`，若将来 Agent 涨到 4+ 或并行度要求变高，补一个 `_agent` 标记即可切到 L3，改动面一个函数。

## 折叠文案按语义分类（重要修正，2026-10-08 中午）

**发现的问题**：原统一文案 `（上一轮由其他专家完成了一次信息检索…）` 对 8 个工具里有 3 个是错的——
`get_user_favorites`（查收藏夹）/ `recall_user_memory`（查记忆）≠ 检索；`compare_products`（对比）≠ 检索。

**为什么必须改（不是文案洁癖）**：把「读取用户偏好」说成「完成信息检索」，下一轮 consult 会形成错误认知
→ 用户问偏好、上一轮"检索过" → 可能**跳过 recall_user_memory 直接编造偏好**。
**文案失真诱发本不该发生的幻觉，比泄漏工具名的代价更大。** 这条正好威胁 `recommend_by_memory` 用例要测的能力。

**改法**：`_TOOL_SEMANTIC_KIND`（工具名 → 语义类别）+ `_FOREIGN_BLOCK_NOTES`（类别 → 文案）+ `_foreign_note(names)`。
块内类别一致用精确文案，跨类别或遇未登记工具退回 `_FOREIGN_BLOCK_NOTE_GENERIC`。
硬约束不变：**文案里出现的必须是语义类别，不能是工具标识符**（实测 8 个工具文案零工具名）。

实测文案：
- search_products / search_catalog / retrieve_knowledge → 上一轮完成了商品与知识检索，具体工具与结果已略
- get_detail → 上一轮查询了单个商品信息，具体内容已略
- compare_products → 上一轮完成了商品对比，具体数据已略
- get_user_favorites / recall_user_memory → 上一轮读取了用户偏好信息，具体内容已略
- load_skill → 上一轮加载了操作流程文档
- 跨类别 / 未知工具 → 上一轮由其他专家完成了一次工具调用，内容已略

**单测 8 条 passed**（新增 `test_collapsed_text_matches_tool_semantics`、`test_mixed_semantics_falls_back_to_generic`）。
写测试时踩坑：先把 `load_skill` 写进越权用例 → 失败，因它是**共享工具不折叠**。断言前先确认白名单归属。
全量 `89 passed, 1 failed`（失败仍是 P2-6 的 PG 依赖）。

### 文案改动后的实测验证（12:36~12:38）

| 用例 | 结果 | 质量 | 过程 | token |
|---|---|---|---|---|
| `recommend_by_memory`（PG未启） | 1/1 | 5/5 | 2/5 | 15,025 |
| `recommend_by_memory`（PG已启，收藏夹有 1 款） | 1/1 | 5/5 | 4/5 | 23,496 |
| `multiturn_switch_consult` | 1/1 | 5/5 | **5/5** | 28,083 |

**无回归**（质量均 5/5、断言 3/3）。附带发现：`recommend_by_memory` 在 PG 启动后**主动多调了 `search_products`**（收藏夹有依据→ 完成推荐闭环），过程分 2/5→4/5；这解释了为何 PG 未启动时该用例过程分低——不是缺陷，是数据缺失。

**但关键事实：降级在这三条里一次都没真正触发。**
`multiturn_switch_consult` 虽是跨轮（turn1 presale → turn2 consult），但 turn1 的调用块里混了共享工具
（`load_skill`/`recall_user_memory`/`search_products` 同时出现在多步响应中）→ `all()` 为 False → 整块保留。
即 **"跨轮混调"与"同轮混调"效果相同，都会绕过降级**——这是比原先注释描述更完整的结论。

**最终判定：在当前 2 Agent / 8:3 工具配置下，降级在真实流量中几乎无法自然触发。**
原因：presale 的典型调用序列（load_skill + recall_user_memory + search_products/get_detail）
必然包含 consult 的 3 个共享工具 → 整块判定恒为保留。**Router 已能100% 正确分类，
第一/二道防线足够，这是第三道冗余保险。**
