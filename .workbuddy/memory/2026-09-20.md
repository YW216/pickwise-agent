## ✅ VS Code Graph 读不到历史的真因与修复（2026-09-20 19:40~20:05）
- **现象**：VS Code 内置「图形」显示"所选源代码管理提供程序没有任何代码管理历史记录"，而 **`git log` 一切正常**；用户补充关键信息"打开别的项目都正常"。
- **真因**：仓库里有且仅有 **1 个缺失对象**——blob `2866c9e2`，对应 `app/agent/rag/knowledge/手机选购指南.md` 的历史版本。它被 `611760d 重建基线` 起**全部 10 个提交**的树引用，但对象文件在最早期损坏中丢失。`git log` 只读 commit 链（所以正常），而 `git gc` / `git rev-list --objects` / VS Code Graph 的**深遍历**（要读 tree 与 blob）一碰到它就 `fatal` 整体退出。
- **定位手法**：`git gc` 主动报 `fatal: unable to read 2866c9e2...` → 「可达对象集合 vs 库内实际对象集合」差集（274 vs 927）确认只缺 1 个 → `git ls-tree -r HEAD | grep <sha>` 找到路径。**踩坑：git 默认对非 ASCII 路径做八进制转义（`core.quotepath`），拿 ls-tree 输出的字符串直接 `Test-Path` 会误判"文件不存在"**——差点因此走错方向。
- **修复**：工作区那份文件内容与历史版本**完全一致**（3529 字节，sha1 相同）→ 用 Python 直接构造 zlib 对象写回 `.git/objects/28/66c9e2...`（`sha1("blob <len>\0" + content)`），绕开 Windows 命令行传中文路径的编码问题。**不是伪造**——内容一模一样，sha 自然吻合。
- **收尾**：`git reflog expire --expire=now --all`（清掉 6 条指向已丢提交的坏 reflog 条目）+ `git gc --prune=now`（927 个松散对象 → 1 个 pack / 274 对象 / 415KB，全部 dangling 清除；`.git` 总大小 0.45MB）。
- **终态验证**：`git fsck --full` **输出 0 行**（无 missing / dangling / broken link）；`git log --all` 10 个提交完整；`git rev-list --objects HEAD` = 274 行正常；`count-objects` 为 `in-pack: 274, packs: 1`。

- **可复用经验（重要）**：**`git log` 正常 ≠ 仓库健康**。判断仓库完整性必须跑会读 tree/blob 的命令——`git gc --dry-run`、`git rev-list --objects HEAD`、`git fsck --full`。只读 commit 链的 `git log` 会掩盖缺失的 blob/tree，而这类缺失恰好会让所有"深遍历"型工具（含 VS Code Graph）静默失败。

**用户定案（写进文档）**：在 head+tail 最小视图策略下，**"缩小条件重查"是唯一自洽的取回路径**；`offset` 分页与 head+tail **错配**——模型看得到"缺了中间一段"，却填不出 offset 该从第几条起（head/tail 是字符级切片，模型不知道中间有多少条）。因此 offset 必须与"**按条截断**（取前 N 条完整 + 声明 total）"配套，二者一起做才有意义，同归「完整截断策略」挂账项。
