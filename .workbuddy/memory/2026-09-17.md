## Langfuse 源码实证（langfuse 4.15.3，环境 `F:\Anaconda\envs\searchagent`）
- 本项目使用的 langfuse 在 **`searchagent` 环境**（另一环境 moai-rag 是 4.0.6）；requirements.txt 未列 langfuse（可选依赖）。
- **`name` 参数是被支持的**：`langfuse/openai.py` 的 `OpenAiArgsExtractor.__init__` 显式接收 `name`，`_get_langfuse_data_from_kwargs` 里 `name = kwargs.get("name", "OpenAI-generation")` → 传给 `start_observation(name=...)`。且 `get_openai_args()` 只回传剩余 kwargs → **langfuse 专用参数被消费掉、不会漏给真 API**。
  → **因此 `reporter.py` 注释里"drop-in 只认 langfuse_prompt / langfuse_public_key 两个前缀参数"是不准确的**（4.15.3 还认 name / metadata / trace_id / parent_observation_id / session_id / user_id / tags）；`sandbox._lf_naming` 的"未包装就不能传 name"顾虑实际不成立（不影响功能，只是多余保险）。
- **上下文机制确认**：langfuse v4 用 **OpenTelemetry context**，其 token 由 **contextvars** 支撑（`_client/propagation.py:101` 注释明写 "OpenTelemetry tokens are backed by contextvars"）。langfuse 在需要跨执行边界保上下文时会**显式** `contextvars.copy_context()`（`_client/observe.py:469,496`）——**反证线程/生成器边界不会自动传递**。
- **langfuse v4 有专门的 `tool` observation 类型**（`LangfuseTool`，见 observe.py 的类型列表），而我们 `reporter.tool_span` 用的是通用 `as_type="span"` → 即使上报成功，Type 列也只显示 SPAN，不会显示 tool。

## ✅ 根因已定位（2026-09-17 上午，两个证据链闭合）
- **证据 1（用户看板）**：`eval:favorites_pick` 的 trace 树只有 3 个 generation + scores，**0 个 tool 节点**；而本地 `runs/favorites_pick.json` 显示该用例**实际成功调用了 4 个工具**（get_user_favorites / load_skill / get_detail / recall_user_memory，全 success=true）→ **工具 span 确实没上报上去**。
- **证据 2（实测实验）**：在项目环境（`F:\Anaconda\envs\searchagent\python.exe`）跑 15 行纯 OTel 探针：主线程 span `valid=True`，`ThreadPoolExecutor` 工作线程里 `trace.get_current_span()` 返回 **trace_id=0 / valid=False** → **OTel"当前 span"不跨线程传递，已实测确认**。
- **证据 3（SDK 源码 `_client/client.py:1395-1405`）**：`_get_current_otel_span()` 在拿到 `INVALID_SPAN` 时打 warning 并 **return None —— "Operations that depend on an active span will be skipped"**。→ **无活动 span 时 span 是被"跳过/丢弃"，不是变成孤儿 trace**。这与"SPAN 计数恰好 = 用例数 20（无多余孤儿）"吻合。
- **根因一句话**：`orchestrator._execute_agents` 无条件使用 `ThreadPoolExecutor`（**N=1 也走线程池**）→ 工具调用与子 Agent 的 ReAct 调用都发生在工作线程 → 工作线程里没有"当前 span" → `tool_span`（以及 drop-in 的 generation）被 SDK **skip 掉**。
- **影响范围**：① 工具 span 全丢；② **子 Agent 的 ReAct generation 疑似也一起丢**（同为工作线程）——`favorites_pick` RunTrace 记 5 次 LLM 调用而树里只有 3 个 generation，与此相符（**需用同一次 run 对齐才能定论**，截图是 14:00 而 json 是 18:58 的跑批）。路由与 Result 调用在主线程，不受影响。

## ⚠️ 本机环境限制（踩坑记录，后续别再重复尝试）
- **删除操作被 fail-closed 拦掉**：本环境把 `Remove-Item`/`rm` 路由到回收站 shim，Windows trash 报 `Some operations were aborted` → 报 `[safe-delete][SAFE_DELETE_FAIL_CLOSED] trash-failed`，文件删不掉。要删临时文件只能由用户手工删（或在资源管理器里删）。
- **bash shell 严重残缺**：`grep` / `tail` / `head` / `ls` / `dirname` / `rm` 全部 `command not found`（PortableGit shim 的 PATH 坏了），`git status --short` 偶发 `fatal: bad object HEAD`（但 `git diff` 正常）。→ **本会话起，文件操作一律走内置 Read/Write/Edit/Glob/Grep；需要 shell 时先试 PowerShell，且 PowerShell 的 stdout 也回不出来，必须 `Out-File` 落盘再用 Read 读**。
