## pi agent 资料辨析（未落盘，仅对话）
- 用户拿到的"pi agent 五步管道"文档（prepareArguments→validate→beforeToolCall→execute→afterToolCall）
  **归属错误**：那套是 Claude Code 系设计（TypeBox、beforeToolCall 权限门），
  pi 官方立场是 "YOLO by default"、明确不做权限检查，两者直接矛盾。
- pi 核心真实的"五步"是 `streamAssistantResponse` 内部序列（上下文变换→convertToLlm→
  解析APIKey→流式调LLM→转发事件就地更新），在模型侧不在工具侧。
- pi 真实工具侧管道是 `executeToolCalls` 四段：校验参数（截断则拒整批）→串行/并行决策
  （看 executionMode）→执行+Hook+进度→结果回填（按模型原始调用顺序，不按完成顺序）。

## 工具系统实测：用户问"查100台笔记本"暴露的问题
实测三个 case（日志已确认）：
1. "查100台" → 模型调 1 次 search_catalog(limit=20)，如实告知 total=20，✅正确
2. "我要100台的信息" → 模型不调工具直接拒绝编造，✅正确
3. "那我要20台的信息" → **模型发 20 次 get_detail**，⚠️真问题
- 真问题形态不是"失控刷调用"，而是**模型为追求信息完整自主升级了任务**
  （用户说"信息"，模型给了"全参数表"，于是必须逐款拉 specs）。
- 熔断挡不住：20 个不同签名，每个只调 1 次；MAX_SAME_CALLS=2 治"重复"不治"穷举"。
- 本次兜住的是"批量并发 + max_react_steps=5"（20 次在一批内发完只算 1 步），
  属数据规模巧合，非机制保障；目录扩到 50 台就会撞步数上限。
