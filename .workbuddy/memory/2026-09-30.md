## 追加：并发问题（已核实，用户决定暂不处理）
用户问"我的工具哪些可以并行、哪些只能串行"。核实结论：

**三层结构**：
1. 单个 Agent 的 ReAct 循环内 —— `app/multi_agent/agents.py:136` `for tc in
   assistant_msg.tool_calls:` **纯串行**（一次 LLM 轮次内多个 tool_call 排队跑）。
2. 多个子 Agent 之间 —— `app/multi_agent/orchestrator.py:264` ThreadPoolExecutor
   **真并行**。
3. 共享工具被并发访问 —— `retrieve_knowledge` / `get_detail` / `load_skill`。

**关键判断**：PickWise **没有任何工具存在串行约束**——工具集全是只读查询（无写后读、
无副作用），缺的不是"串行保护"而是"并行执行的实现"。也没有 pi 的 `executionMode`
概念（不是全标串行，是根本没做这个区分）。若将来要并行回填，必须**按模型原始调用
顺序**排序（否则 tool 消息顺序与 tool_calls 对不上，DeepSeek 会报错）。

**线程安全性核实（读四个类源码后的结论）**：
| 类 | 共享可变状态 | 判定 |
|---|---|---|
| `Embedder` | 仅 `_client`(OpenAI)，`encode` 无状态调用 | ✅ 安全 |
| `MilvusBackend` | `_client`/`_loaded`/`_size_cache`/`_embedding_model` | ⚠️ 真风险 |
| `KnowledgeRetriever` | `_loaded` | ⚠️ 真风险 |
| `SkillManager`/`SkillMeta` | `_skills`(只读) / `body`+`_body_loaded` | ⚠️ 半风险(幂等重复) |

- **最要紧**：`milvus_backend.py:47 _ensure_client` 的 check-then-act——两线程同时
  过 `is None` 判断会各建一个 MilvusClient，**后写覆盖先写且被覆盖者永不 close，
  gRPC channel 泄漏**。`load()`(:246) 更重，一次改四个字段。
- `retriever.py:36/49` 的 `_loaded` 与 backend `_loaded` 是**两个独立标志位**，
  竞态被放大一层。
- `skills/loader.py:33 SkillMeta.load_body` 竞态但**幂等**（重复读文件+解析，结果正确），
  严重性远低，可不处理。
- **重要前提澄清**：风险**当下就已存在**，不是改了并行才有——因为 `_retriever` /
  `_skill_manager` 是**模块级全局单例**，两个子 Agent 经 ThreadPoolExecutor 同时
  调 `retrieve_knowledge` 时就会撞上。
- **若将来修**：最小修法是给 `_ensure_client` + `load()` 加 `threading.Lock`
  （double-checked locking），**且必须同时处理 retriever 那层**，否则锁只包底层、
  上层照样重复调用，等于白加。
- **用户决定：并发问题暂不处理**（2026-09-30）。

## 追加：工具并行执行 —— 设计方案与度量探针（已交付）
用户回到"工具的并行执行"话题。核实关键事实后给出方案：

**关键发现（改变了难度评估）**：熔断器**不是 ToolManager 的状态**，而是调用方逐轮
持有的 `seen` dict（`manager.py:93` 由 handle 传入，`registry.py:351` 读写）。
`ToolManager` 本身**无状态**（只有构造期定死的 `_tool_defs`/`_tool_source`）。
→ 并行改造**不需要给 ToolManager 加锁**。

**核心方案：闸门串行、执行并行**（两阶段）
- 阶段 1（主线程）：`for` 依次过三道闸门（解析/校验/熔断，顺带更新 `seen`），
  产出 pending 清单 + `slots = [None] * n` 预分配槽位。语义零改变。
- 阶段 2（线程池）：仅执行 pending，`seen=None` 传入（熔断已在阶段 1 完成，
  避免二次共享状态），结果按**原始索引**写回槽位（不按完成顺序，否则
  DeepSeek 会因 tool 消息顺序与 tool_calls 不匹配报错）。
- 改动**集中在 `app/multi_agent/agents.py` 一处**，manager/registry 不动。
- 注意：`max_workers` 要封顶（如 `min(len(pending), 8)`），防 20 个调用开 20 线程。

**必要性判断（重要）**：并行最大受益场景（20 次 get_detail）正是上一轮 prompt 改造
要消灭的行为，存在错位。常规批次 1~4 个，净省约 240ms ≈ 总延迟 8~15%。
→ 结论：**值得做但不紧急，且必须先量**。

**前置依赖**：并行会高频触发共享工具懒加载竞态 → 必须**先给
`MilvusBackend._ensure_client` + `KnowledgeRetriever.load` 加锁，再做并行**。

**已交付度量探针**：`tests/measure_tool_concurrency.py`（只读，不改业务代码）
- 原理：monkey-patch 三处 —— `ToolManager.execute_tool`（计时，唯一汇聚点）、
  `SubAgent._complete`（LLM 计时 + 推进 step）、`SubAgent.handle`（重置 step 计数）。
- 用 `threading.local()` 携带 agent/step 标签，避免多子 Agent 并行时记录串号。
- `RoundRecord` 按轮分组记耗时，**精确**算并行收益：串行 = sum，并行 ≈ max。
- 报告 5 段：批次规模分布 / 各工具耗时 / 逐批次并行收益明细 / 耗时占比 / 结论
  （自动给建议：<3% 不做、3~8% 边际、>8% 值得做）。
- 自检通过：模块导入 OK、三个 patch 均装上、空数据报告不崩。
- 未跑（按约定用户自跑，会真实调 LLM + DB 产生 token 消耗）。

## 度量结论：并行改造正式否决
**两次实测数据**：

**① 查询类（"我要20台笔记本的信息"）**
- 端到端 18.86s｜路由 5.72s｜Agent 执行 5.30s｜其他 7.85s
- 工具调用 1 次 `search_catalog` = **22ms**｜LLM 2 次 = 5.27s
- 可并行批次 **0/1**；工具占 Agent 执行段 **0.4%**
- 附带验证**方案三成功**：模型主动说"共 34 款、单次最多 20 款"并引导补充条件

**② 检索类（"保修政策是什么" + "七天无理由退货怎么算"）**
- 问题1：端到端 18.46s｜工具 4.94s（占 Agent 段 40.1%）｜可并行批次 **0/3**
- `retrieve_knowledge` 3 次：**4065ms / 459ms / 413ms**，平均 1645ms
- 问题2：1 次 1213ms

**核心结论**：
1. **并行改造收益 = 0**，理由是**可并行批次 0/3**——三次检索分属三个不同步
   （步与步之间有 LLM 决策），天然不可并行。不是"工具太快"，是**批次大小 = 1**。
2. 工具分两类量级：查库类 22ms，检索类 400~4000ms。**都救不了并行**。
3. **"只读 ⇒ 并行一定更好"是错误推理**：只读只保证并行**安全**，不保证有**收益**。
   收益取决于①同批≥2个 ②单次耗时大 ③下游能扛并发，三条同时满足。
   且只读也可能有副作用（限流/配额/连接池），并行反而更差。

## 【重要修正】并行结论两次被实测推翻
**第一次修正**：实测「我想买台电脑」，模型在第 2 步**同批发 2 个调用**
（`recall_user_memory` + `search_products`）。→ **"模型从不并发"是错的**。
- `load_skill` 被单独拆出一步**是合理的**：它是"计划性"调用，模型要先看技能流程
  才知道该调什么，依赖真实存在。判据是"依赖关系"，不是"调用数量"。

**第二次修正**：针对性实验「保修政策是什么，顺便说一下七天无理由退货怎么算」→
**1/1 批次 100% 可并行**，两个 `retrieve_knowledge`，串行 2692ms → 并行 2283ms，省 **409ms**。
- **关键机制：并行只能省"快的那个"**。2283ms 是冷启动，409ms 是复用连接后的。
  并行 = max(2283, 409) = 2283ms，慢的该等还得等。
- 409ms / 12.41s = **3.3%**（占 Agent 段 5.2%）。

**最终结论（三次迭代后）**：不是"不能做"，也不是"没收益"，而是
**"收益与代价不匹配"** —— 最好情况 409ms(3.3%)，日常批内单调用收益≈0；
成本是改 ReAct 核心循环 + 加并发锁 + 加并发测试。判定：**不做**。
- **根本原因：工具耗时极度不均匀**。唯一慢的是 `retrieve_knowledge`(400~4000ms)，
  其余全是 0~22ms（`compare_products` 0ms 内存快照、`search_catalog` 22ms PG）。
  批内只要有一个毫秒级调用，并行收益必然趋近 0。
- 触发条件（任一出现才重评）：①引入慢工具 ②引入写操作 ③批次稳定变大。

**已写入文档**：`develop_docs/模块设计总结/工具系统总结.md` 的「# 为什么不做工具并行」
整节重写（含结论表、五次实测汇总、成本收益分析、实施路径、面试快问快答 6 问）。
旧版内容已作废（原写"模型全是 1 个调用"，与实测矛盾）。
